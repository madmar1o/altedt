# Методология TDD (Test-Driven Development)

## Обзор

В проекте применяется методология разработки через тестирование (TDD). Основной цикл:

**Красный -> Зелёный -> Рефакторинг**

```
1. Написать тест (не проходит)    ← Красный
2. Написать код (тест проходит)   ← Зелёный
3. Рефакторинг (тесты всё ещё проходят)
```

## Цикл разработки (TDD Loop)

### Этап 1: Написать тест (RED)

```bash
# 1. Понять требование
# 2. Написать тест, который описывает ожидаемое поведение
# 3. Запустить тест - он должен ПАДАТЬ
npm test -- --grep "название-теста"
```

**Правила:**
- Тест пишется ДО кода
- Тест должен быть конкретным и изолированным
- Тест должен падать по явной причине (не из-за ошибки компиляции)
- Один тест = одна проверка

### Этап 2: Написать код (GREEN)

```bash
# 1. Написать минимальный код, чтобы тест прошёл
# 2. Запустить тест - он должен ПРОЙТИ
npm test -- --grep "название-теста"
```

**Правила:**
- Писать только тот код, который нужен для прохождения теста
- Не добавлять "на будущее" функциональность
- Не беспокоиться о качестве кода на этом этапе

### Этап 3: Рефакторинг (REFACTOR)

```bash
# 1. Улучшить качество кода
# 2. Убедиться, что тесты всё ещё проходят
npm test
```

**Правила:**
- Тесты не должны меняться (кроме случаев когда требование изменилось)
- Код должен оставаться чистым и поддерживаемым
- Все тесты должны проходить после рефакторинга

## Пример цикла TDD

### Задача: Добавить функцию расчёта суммы двух чисел

**Шаг 1: Написать тест (RED)**

```typescript
// src/test/math.test.ts
import * as assert from 'node:assert';
import { add } from '../../src/math';

suite('math', () => {
    test('add should return sum of two numbers', () => {
        assert.strictEqual(add(2, 3), 5);
    });
});
```

Запуск:
```bash
npm test -- --grep "add should return"
```
❌ Тест падает (функция add не существует)

**Шаг 2: Написать код (GREEN)**

```typescript
// src/math.ts
export function add(a: number, b: number): number {
    return a + b;
}
```

Запуск:
```bash
npm test -- --grep "add should return"
```
✅ Тест проходит

**Шаг 3: Рефакторинг**

Код простой, рефакторинг не требуется. Все тесты проходят.

## Требования к тестам

### Названия тестов

Используйте описательные названия на русском языке:

```typescript
test('функция add возвращает сумму двух чисел', () => {
    // ...
});

test('при отрицательных числах add возвращает правильный результат', () => {
    // ...
});
```

### Структура тестового файла

```
src/test/
    features/        # Тесты фич (базы, запуск, отладка)
    shared/          # Тесты общих утилит
    metadata/        # Тесты метаданных
    testing/         # Тесты системы тестирования
    tools/           # Тесты инструментов
    utils/           # Тесты утилит
```

### Каждый тест должен:

1. Проверить одно поведение
2. Быть автономным (не зависеть от других тестов)
3. Быть быстрым (не более 100мс)
4. Иметь понятное название
5. Использовать assert для проверок

## Интеграция с Git Flow

### Feature-ветка + TDD

```bash
# 1. Создать feature-ветку
git checkout develop
git checkout -b feature/новая-функция

# 2. Цикл TDD для каждой функции:
#    - Написать тест (RED)
#    - Написать код (GREEN)
#    - Рефакторинг

# 3. Запустить все тесты
npm test

# 4. Зафиксировать изменения
git add .
git commit -m "feat(функция): описание реализации"

# 5. Создать PR в develop
```

### Pull Request чеклист TDD

- [ ] Все тесты проходят (`npm test`)
- [ ] Каждый новый функционал покрыт тестами
- [ ] Покрытие кода не снизилось
- [ ] Тесты написаны ДО кода (может быть проверено в коммитах)
- [ ] Нет избыточного кода без тестов

## Пример TDD для редактора форм

### Задача: Добавить кнопку "Добавить элемент" в редактор форм

**Тест (RED):**

```typescript
// src/test/features/formEditor.test.ts
import * as assert from 'node:assert';
import { FormEditor } from '../../src/features/formEditor';

suite('FormEditor', () => {
    test('addElement should add new element to form', () => {
        const editor = new FormEditor();
        editor.addElement({ type: 'button', name: 'btn1', caption: 'Кнопка' });
        assert.strictEqual(editor.getElements().length, 1);
        assert.strictEqual(editor.getElements()[0].name, 'btn1');
    });
});
```

**Код (GREEN):**

```typescript
// src/features/formEditor.ts
export class FormEditor {
    private elements: any[] = [];

    addElement(element: any): void {
        this.elements.push(element);
    }

    getElements(): any[] {
        return this.elements;
    }
}
```

**Рефакторинг:**

Добавить валидацию, типизацию, обработку дублей имён и т.д.

## Regeln (Правила)

| # | Правило |
|---|---------|
| 1 | Тест пишется перед кодом |
| 2 | Один тест проверяет одно поведение |
| 3 | Тест должен падать до написания кода |
| 4 | Код пишется только для прохождения теста |
| 5 | Все тесты должны проходить после рефакторинга |
| 6 | Нет кода без тестов |
| 7 | Тесты не должны зависеть друг от друга |
| 8 | Названия тестов на русском языке |
| 9 | Все тесты запускаются перед коммитом |
| 10 | Покрытие кода не ниже 80% |

## Антипаттерны TDD

| Антипаттерн | Почему плохо | Решение |
|-------------|-------------|---------|
| Тесты после кода | Сложно 달성ть 100% покрытие | Писать тесты trước кода |
| Один тест на всё | Сложно понять что сломано | Маленькие изолированные тесты |
| Тесты зависят от порядка | Нестабильные результаты | Каждый тест независим |
| Игнорирование падающих тестов | Накопившийся технический долг | Исправлять сразу |
| Тесты на реализацию | Хрупкие тесты | Тестировать поведение, а не детали |

## Чеклист перед коммитом

```bash
# 1. Все тесты проходят
npm test

# 2. Линтер проходит
npm run lint

# 3. Покрытие кода в норме
npm run test:coverage

# 4. Типы корректны
npm run typecheck

# 5. Коммит с правильным сообщением
git commit -m "test(компонент): описание"
```
